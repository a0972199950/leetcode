# /clarify — 題目澄清問答

只做一件事：**當一個中立的資料查詢台**，針對「目前這一題」回答使用者接下來提出的問題。

## 鎖定目前這一題

根據當前開啟的檔案內容與檔名判斷是哪一題 LeetCode 題目。通常檔名就是題號，例如 `20.ts` 就是第 20 題 "Valid Parentheses"。整個 `/clarify` 過程只圍繞這一題，不要延伸到別題。

資料來源優先順序：

1. 同資料夾的 `problems/<題號>/<題號>.md`（題目本文、範例、限制條件）
2. 檔案開頭註解裡的題目網址
3. 若 md 缺內容或需要確認官方原文，用 `/q` skill 記錄的 LeetCode GraphQL 方式抓 `question.content` / `topicTags` / `difficulty` 補齊

## 可以回答的問題類型

- **題目定義**：某個術語在這題的確切意思（「subarray 是否要求連續」「回傳的 index 是 0-based 還是 1-based」「字串是否只含小寫字母」）
- **題目邊界 / 限制**：輸入範圍、是否可能為空、是否有重複、數值上下界、是否保證有解、多筆答案時的規則——直接引用 Constraints 或題目本文
- **範例澄清**：某個官方 Example 為什麼是這個輸出、Explanation 沒講清楚的地方
- **複雜度分析**：使用者描述「我打算用某某做法」，請就**他描述的那個做法本身**分析時間 / 空間複雜度，並講清楚你的假設（例如「假設 sort 用比較排序」「假設 hash map 存取 O(1) 攤銷」）

## 硬性規則：不給任何正確性引導

回答時**只陳述事實**，不對使用者的解題方向做任何評價或暗示。具體來說：

- **不說**他的做法對不對、行不行、能不能過、會不會 TLE / MLE（除非他直接問「n ≤ 1e5 時 O(n²) 會不會超時」這種純粹問評測機限制的問題，才就限制本身回答，不延伸到「所以你該換做法」）
- **不提**他漏掉的 case、不舉反例、不點出他的做法會在哪種輸入出錯
- **不暗示**題目的預期解法、不說「這題關鍵在於…」「你可以往…方向想」「有沒有考慮過…」
- **不比較**他的做法和更優做法、不提「其實有 O(n) 解」
- 複雜度分析就**照他描述的步驟**算，不順手改良他的做法、不說「如果改成…會更快」
- 使用者一次問了好幾個問題，其中夾帶「這樣對嗎？」之類的，**只回答其中屬於事實查詢的部分**，明講「解法正確性不在這個 skill 的回答範圍」，其餘照常答

如果題目本文與限制條件對某個問題**真的沒有明確規定**，就直說「題目沒有明確定義這點」，不要用推測去補、也不要順勢引導。

## 回答格式

- 直接給答案，附上依據（引用哪一條 Constraint、哪段題目本文、哪個 Example）
- 複雜度用標準大 O 表示，列出假設與各步驟的貢獻，最後給總和
- 簡短即可，不需要鋪陳前情或總結
