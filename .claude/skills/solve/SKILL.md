# /solve — 直接給出完整解法

不同於 `/judge` 的引導式教學，`/solve` 不提問、不分層鋪陳，直接把答案端出來。

## 鎖定目前這一題

先判斷這題是標準 LeetCode 題目，還是自訂題目（自訂題目不一定有題號對應的資料夾，題目敘述可能直接寫在檔案開頭的註解裡）。

**標準 LeetCode 題目**：通常檔名就是題號，例如 `20.ts` 就是第 20 題 "Valid Parentheses"。資料來源優先順序：

1. 同資料夾的 `problems/<題號>/<題號>.md`（題目本文、範例、限制條件）
2. 檔案開頭註解裡的題目網址
3. 若 md 缺內容或需要確認官方原文，用 `/q` skill 記錄的 LeetCode GraphQL 方式抓 `question.content` / `topicTags` / `difficulty` 補齊

**自訂題目**（沒有 `problems/<題號>/<題號>.md`，或檔名／資料夾不是純題號）：題目敘述以**檔案開頭的註解**為準，包含題意、範例、限制條件都可能寫在那裡。不要因為找不到 md 檔或題號就假設抓錯題目或嘗試套用 LeetCode GraphQL 查詢——這種情況下註解就是唯一且權威的題目來源，照著它理解題意即可。若註解裡的敘述有不清楚或缺漏的地方（例如沒寫清楚邊界），可以在「簡單的解析」段落之前先簡短點出你的假設，不用中斷流程去追問。

## 輸出格式：只給以下三個部分，依序輸出，不要多加別的段落

### 1. 需使用到的演算法與複雜度

- 條列本題核心會用到的演算法／資料結構關鍵字（例如：Two Pointers、Monotonic Stack、BFS）
- 給出時間複雜度與空間複雜度，並簡述複雜度怎麼算出來的（哪個操作跑幾次、額外佔用多少空間）

### 2. 完整答案

- 直接給出能通過該題所有官方測資的完整 TypeScript 實作
- 程式碼風格照專案慣例：
  - 變數命名講人話，不用單字母縮寫硬湊
  - 用 explicit 的迴圈／stack 結構，不用過度壓縮成單一 accumulator／兩個變數互相推導的寫法（那種寫法即使行數短，也難從頭重推，不採用）
  - 理論上不會走到的 fallback 分支，用 sentinel return 收尾，不用 `throw`
  - 若用到 trick（哨兵值、巧妙的 index 約定、邊界取在範圍外等讓程式碼變短但推理變難的手法），要用註解簡短標明「這是 trick，用來換取什麼」

### 3. 簡單的解析

- 用最短篇幅講清楚這個解法「為什麼對」、關鍵想法是什麼
- 不用像 `/judge` 那樣從暴力解逐層鋪陳，直接針對給出的最終解法講核心邏輯即可
- 若有需要特別處理的邊界條件，順帶點出來

## 與 `/clarify`、`/judge` 的分工

- `/clarify`：只答題目定義／邊界問題，不給任何解法方向
- `/judge`：針對使用者已寫的解法，用提問引導逐層優化，不直接給答案
- `/solve`：直接給出完整答案，不引導、不分層、不提問

`/solve` 只負責輸出上述三個部分，不主動修改使用者的解法檔案，也不更新 `PROGRESS.md` / `SESSION.md`。
